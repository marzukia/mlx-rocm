# R4 design (scratch — do not commit)

## Root cause (from R3, verified in code)
- Per-step token Load (mx.array([[t]])) evals in the PREVIOUS step's tail, BEFORE the
  mode pre-activation (arm = step end) and before gd_step_prepare (next step's first op).
  So `Load::eval_gpu`'s slot path (gated on `graph_decode_mode()`) never fires.
- The fresh-capture `stage_slot16` kernel node is INSIDE the captured graph and re-runs
  on every replay launch: it copies the capture-time arena idx buffer (which keeps holding the capture token) into the slot AFTER the pre-launch H2D. So even if a Load wrote the slot, the node clobbers it. The gather reads the slot -> capture token.

## Fix (a): deliver at Load time, independent of pre-window mode timing
1. device.cpp: new persistent post-arm flag `g_gd_idx_persistent`
   (env-gated like the mode: MLX_GRAPH_DECODE=0 disables),
   `gd_idx_persistent()` / `set_gd_idx_persistent(bool)`.
   - set true: gd_step_prepare (arena secured; covers capture+replay first ops),
     the arm-time block (eager_end arming, next to the existing mode pre-activation).
   - set false: gd_tear_down, and the big/micro retract in gd_on_op.
2. load.cpp: slot-path gate `graph_decode_mode()` -> `gd_idx_persistent()`.
   After the slot H2D, ALSO refresh the recorded capture-time idx buffer VA
   (arena, stable above the floor): the re-run stage node then propagates the
   NEW token into the slot (node runs stream-after the pre-launch H2D).
   Guard: only if arena active AND in_decode_arena(va) (arena realloc -> dangling;
   re-capture case where src == slot VA -> skip, that graph has no stage node).
3. allocator: `decode_idx_set_src_va(void*, size_t)` + getters
   (`decode_idx_src_va()`, `decode_idx_src_nbytes()`).
4. indexing.hip: in the fresh-capture (!took) branch, record the src VA
   alongside the stage node.

## Why both writes are needed
- slot write at Load time: needed when the re-capture's graph has NO stage node
  (re-capture consumed the Load: take()=true -> no node recorded).
- arena-src refresh: needed when the graph HAS the stage node (original capture):
  the node re-copies arena->slot on every launch and would clobber the slot write.
- First capture: Load predates arming (persistent=false) -> falls through as before,
  stage node recorded + src VA recorded. Both orderings (Load before/after the arm)
  work.

## Must not destabilize
- op-84 first-replay divergence -> discard -> re-capture (pilot failsafe):
  our change touches no op sequence; discard path skips stale VA via the arena check.
- value slots (copy.hip:343) stay mode-gated; only the idx Load path changes.

## Verification (per brief)
- [gdidx] load: fires once per step in G (non-zero slot arms, take()=1 per gather).
- 3x A / 3x G / 3x MTP4c battery; G ALLTOKS md5 == A (de160355...), FIRST20 match,
  no 264 attractor; G median > A median and > 74.4; MTP4c ~43.6 + acceptance match.

## R4 fix (t1595): staging moves OUT of the capture window

Diagnosis (gd4 battery + G1Y debug, 64-token G run):
1. First capture: idx buffer shadow is NULL in-window -> stage node NOT recorded
   in-window; it gets recorded in the first REPLAY step (shadow then exists),
   AFTER the graph was built. Replay reads the baked STALE capture-time idx VA
   -> 264 attractor (20/20 identical).
2. Re-capture (after discard): shadow exists in-window -> the in-window hipMemcpy H2D is a BLOCKING legacy-stream op -> 906 during capture ->
   stream tainted -> first op of the re-capture crashes
   (hipLaunchKernel ... previous error during capture).
3. The Load path (the "bench-flow" theory) fires 0 times, same as R3: bench-flow token delivery is the gather shadow-refresh + staging node, not the Load.

Fix (commit 5b1bb4b):
- indexing.hip fresh branch: NO hipMemcpy in-window at all. Record the stage
  node (src = persistent staging buffer, dst = persistent idx slot) and a
  PENDING SEED (plain memory write: the capture step's per-step idx buffer
  device VA; safe in-window).
- device.cpp decode_capture_end_record: between hipStreamEndCapture and worker_->signal_now() (the deferred buffer frees), consume the seed and hipMemcpy D2D (staging src <- capture idx buffer, still live). The blocking
  D2D completes BEFORE the graph launch is issued, so launch #1 carries the
  capture step's token; replay launches carry the per-step refresh (pinned-
  shadow H2D in the replay branch, or the Load path).
- The per-step idx buffer VA cannot be the node source directly: it is a plain malloc buffer at the capture step (arena activates later / step-end offset at replay), freed after the step -> the 264 attractor.

Battery (pending, on the gd4fix wheel): A.1 = 71.69 t/s FIRST20-canonical
(already green, 0919e032 wheel); G.1-3 + MTP4c.1 guard on the fixed wheel.

## R4 fix #2 (t1595): the in-window op was the fill-loop gpu_ptr flush

Second battery on 5b1bb4b (b0e96a56 wheel): A.3 = 74.40 t/s, FIRST20
canonical (regime confirmed); MTP4c.3 green; G.7-9 still crash. G.7
sequence: capture#1 OK -> replay discards (op-84 divergence, failsafe) ->
arm -> first op of capture#2 (the bench argmax) dies with
"hipLaunchKernel failed: operation failed due to a previous error during capture".

Root cause: the 5b1bb4b end_record D2D is NOT the crash source (it runs after EndCapture). The crash source is the gather's fill-loop flush
(indexing.hip: `h_indices[i] = gpu_ptr<void>(inputs[i+1])`): gpu_ptr
flushes a dirty pinned shadow with a BLOCKING hipMemcpy, which 906s inside a capture window. Capture#1: the per-step idx buffer's lazy shadow is null -> the flush is a no-op -> the window stays clean. Re-capture:
the shadow exists and is dirty (the bench rewrites the token) -> the blocking H2D fires in-window -> the stream is tainted -> the re-capture's first launch fails. The 5b1bb4b "pending seed" gpu_ptr call hit the same
flush; the seed itself was not the problem.

Fix (commit 43b1769): all in-window copies are RECORDED (captured), never run blocking:
- allocator shadow_chunked_copy: when stream_capturing(), the H2D flush issues ONE hipMemcpyAsync on the capture stream (new accessor capture_stream()/set_capture_stream(), set at BeginCapture, cleared at
  EndCapture) - the flush is captured and re-executes at every launch, reading the pinned shadow at launch time. D2H readbacks keep the
  blocking path (a recorded D2H would hand the host stale bytes;
  in-window readbacks are deferred via the worker).
- indexing.hip fresh branch: the staging-source seed is an async memcpy
  RECORDED on the capture stream - H2D from the pinned shadow when it exists, else D2D from the per-step idx buffer's device VA (the recorded buffer-creation H2D precedes it in stream order, so launch #1
  delivers the capture step's token). The end_record D2D and the set_seed/consume_seed allocator API are gone.
- indexing.hip replay branch: the per-step refresh is a blocking D2D
  (staging src <- per-step idx buffer) OUTSIDE the window (replay steps are not captured). This also fixes a latent R3-design flaw: the bench creates a FRESH per-step idx array (mx.array([[t]])), so the buffer's lazy shadow is null and never holds the new token - the pinned-shadow refresh would have delivered the previous token (attractor). The buffer's device value is authoritative: its creation H2D already ran.

Token flow after 43b1769:
- capture step: [recorded] creation H2D (idx buffer = token) -> [recorded]
  seed memcpy (staging src <- shadow or idx buffer) -> [recorded] staging
  node (slot <- src, zero-fill the rest) -> gather reads the slot.
- replay step: creation H2D (eager) -> blocking D2D (staging src <- idx buffer) outside the window, before the launch -> launch re-runs the staging node (slot <- src) -> gather reads the slot.
- Load-delivered step (took): load.cpp refreshes the staging src directly.

## R4-fix (t1655): per-gather indirect-idx delivery (v2)

The 3f35385 R4 head crashed on the FIRST capture (the 906 class): its
in-window replay branch was `!fresh && !took` with a GLOBAL fresh flag
and a single global src/slot pair, so the second in-window seed gather took the "replay" branch inside the window (a blocking hipMemcpy D2D on the legacy stream, 906, taint surfacing at the next launching op).

The first fix round (per-gather 16 B staging buffers + the out-of-window blocking D2D refresh + the recorded seed copy) removed the crash but reproduced the 264 attractor: the bench makes a FRESH per-step idx array (a plain mx.array, not a Load - the Load path never fires in
MTP=0 decode), and the recorded seed D2D re-read the FREED capture-step
idx buffer VA on every launch, clobbering the pre-launch refresh with the capture step's token. A recorded node may only ever read a STABLE
VA; the per-step idx buffer's VA is never stable, so the token cannot
be staged from it in-window. v2 delivers the POINTER, not the token:

1. Per-gather indirect-idx delivery: each in-step single-row gather k
   (the in-step ordinal resets with the arena, so capture and replay steps map identically) owns an 8 B PINNED host buffer holding the current per-step idx buffer's device VA (the gather op rewrites it
   IN PLACE every step - no hip call) plus an 8 B persistent device pointer slot. The slot is written by an async H2D (pinned source, no
   allocation, NO blocking copy - capture-safe; a recorded node only
   ever reads a stable VA), which when recorded re-executes at every graph launch re-reading the CURRENT pinned host contents (the persistent re-delivery pattern). The indirect gather kernel
   (gather_rows_ind_kernel) dereferences the slot and reads the live per-step idx buffer - neither the token nor its buffer's VA is baked into the recorded kernel. >4 in-step single-row gathers fall back to the direct per-step idx read (h_indices default). The 4-pair bound
   mirrors the K=4 value-slot convention.
2. The second in-window gather takes ITS OWN pair: there is no shared staging flag and no shared source, so it cannot hit a blocking copy or a neighbor's value. There is NO blocking hip* anywhere on the path - the first-capture crash class is out by construction (the explicit capture-stream window test is therefore unnecessary for
   safety; it remains in the debug log).
3. Buffer lifecycle: the 4 pointer pairs live in words 1..4 of the persistent 4 KB slot buffer and its 4 KB pinned host twin (word 0 is the token slot/shadow, the Load path). Materialized at arm and at prepare (decode_idx_ptrs_materialize, BEFORE the capture window - a hip* during a capture invalidates the exec on ROCm 10.1) and NEVER
   freed (each slot VA is baked into every exec that references it; a
   lazy allocation inside the window is refused and the gather falls back to the direct read). No per-incarnation records (there is
   nothing to reset at a fresh capture; the pinned shadows are rewritten
   in place by every step's gather op).
4. The slot arm survives to the step's first gather: it is set by the token Load in the previous step's tail (BEFORE the arm/prepare), so the arena reset no longer clears it. The Load-timing gate is the RAW
   ENV ENABLE (graph_decode_env_enabled, MLX_GRAPH_DECODE != 0) instead
   of the post-arm persistent flag - the per-step token Load lands in the previous step's tail, before the arm and before the next step's prepare, so the persistent flag was already the wrong timing (0 load lines on the bench). When the Load path fires, the per-step idx array is a VIEW of the persistent slot buffer, and the gather's indirect path reads the slot through the pointer slot - the slot
   write (the 16 B H2D) is the per-step delivery. (In MTP=0 decode the
   bench's per-step idx is a plain mx.array, not a Load, so this path
   does not fire; the indirect path above is the delivery.)

Multi-seed in-window case (stated explicitly): a capture step with k single-row gathers records k H2D nodes and k indirect gather kernels in
window (all stream-ordered, none blocking); the single global state of
the 3f35385 head is gone - there is no shared `fresh` flag, no shared
src buffer, and no blocking copy anywhere, so the second (or third, or fourth) in-window gather cannot reach a blocking op. The explicit
window test (capture_stream() != nullptr) is no longer load-bearing for
safety (no blocking op exists to gate); it remains in the debug log.
