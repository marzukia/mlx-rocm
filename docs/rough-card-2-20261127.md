Lane context: the first card (ISTA-DASLab GSQ-RCO IQ2_S-mtp 9.61G, ACCEPTED ROUGH) rides monky's queue - the 4-item record (load+coherent 1024 at IQ2_S-mtp; MTP on/off; IQ2_S vs IQ2_XS; KV q8_0 vs f16 at 4096), neon file IQ2_S-mtp first, fallback chain IQ2_S -> IQ2_XS-mtp -> QSA IQ2_S. This card is the next CPU-side lead set in the three named categories, all verification CPU-side (in-tree source reads, pinned-dep reads, published HF material, in-lane records); box facts by role: the box = RX 9070 XT gfx1201 16GB dGPU.

## Category 1 - config levers from the ISTA plots

The plots are located: the HF repo card ships two headline plots (plus three per-benchmark plot companions) - `Qwen3.8-27B-task_avg_vs_avg_bit_width.png` (quality vs bit-width) and `Qwen3.8-27B-mtp_speculative_decoding.png` (speculative decoding with the MTP head; published llama.cpp bench, 3 draft tokens, 12 categories x 4 quants). Content beyond the text tables is image-only; the levers below rest on the text-extractable parts (the published bench summary + the README numeric tables), labeled as such.

1. MTP speculative on/off on the -mtp file (the headline lever; evidence: the MTP plot's published bench, MEASURED published on their hardware, not ours): 101.6-118.0 tok/s across 12 categories x 4 quants (IQ2_S 103-116; peak multilingual IQ2_XS 118.0). Expected effect on the box: a bandwidth-efficiency class of ~2.4x plain AR (a cycle = 1 main pass ~9.6G + K x 0.35G draft passes, ~2.5-2.9 output tokens per cycle at the published 54.2% mean acceptance) - the ceiling is arithmetic, the floor is the kernel path (see Category 3). Test: the MTP-on arm vs the AR baseline, same file, same prompt, recorded tok/s + tokens/step + HBM.
2. Draft-token count K (the bench used 3; our stack's in-tree spec-decode mode class): `MLX_MTP=3` = K=2 (one S=3 batched verify - the 0.3.0 record protocol, 111.01 t/s banked on the 9B-class vehicle) and `MLX_MTP=4` = K=3 (one S=4 batch). Each extra draft token costs +0.35G of weight reads and its acceptance decays geometrically (at 54.2%: position-2 ~= 29%, position-3 ~= 16%), so K=3 is marginal unless measured acceptance beats the published mean. Expected: K=2 is the efficiency sweet spot; K=3 only if acceptance on the lane prompt class runs high. Test: the K=2 vs K=3 arm (if the vehicle exposes the mode class), one round each.
3. The n-gram zero-cost fill (in-tree `MTP6_NGRAM`/`MTP6_NGRAM_S3` class, `MTP6_NGRAM_N=4`): a hit replaces a draft forward with a table lookup - free acceptance on repetitive text, zero weight reads. Expected: a small free throughput bump, largest on word-salad/repetitive prompt classes (the lane's d500x-class prompt is exactly that class). Test: fill on vs off, if the vehicle supports it - cheap, one round.
4. Quant-file selection (IQ2_S 9.26G / 2.75bpw vs IQ2_XS 8.42G / 2.50bpw) from the task-avg plot's text tables: IQ2_S = 89.5 task-avg (97.4% of the 91.87 base), AIME25 100.00, ZS 101.8% recovery; IQ2_XS = ZS 100.3%, AIME25 96.67. The MTP-plot fact that draft acceptance is QUANT-INVARIANT (all four quants within ~2-4 pts of each other) means the file choice is a pure quality/fit trade, never an MTP trade. Expected: IQ2_S stays the selection; IQ2_XS only for HBM pressure.
5. The step-up operating points (task-avg plot, text tables): IQ3_XXS 3.0bpw 10.1G = 91.1 task-avg, AIME25 100.00; IQ3_S 3.5bpw 11.8G = 91.7 ~= task-lossless (AIME25 + LCB v6 exact match, GPQA-D -0.51). Both fit the 16G box with the 0.35G head + q8_0 KV. Expected: only if the quality axis ever outranks the 2.5-bit class; noted so the lane has the names and sizes ready.
6. KV-cache class (from card 1's config list, kept for completeness): q8_0 vs f16 at 4096 context - f16 KV on 27-class layers would eat the 16G budget before context; q8_0 is the fit. Already monky's item 4; listed so this card's lever set is the union, not a superset gap.

GAP (named): the two published plots are PNGs; the lane record's text extraction covers the published bench summary (101.6-118.0 tok/s, 12 categories x 4 quants, 3 draft tokens, 54.2% mean acceptance, 49-62% per-category), the multilingual peak (IQ2_XS 118.0) and the IQ2_S range (103-116). Per-category x per-quant acceptance and throughput cells beyond those are image-only and were NOT text-extracted on this pass - any lever that would need the full acceptance matrix (per-category tuning, category-mix weighting) is blocked on the plot being re-published as data. That is the single unresolved ISTA-plot gap.

## Category 2 - quant options for the draft/MTP side

The -mtp build carries the 15-tensor MTP head at high precision (+0.35G, 9.26 -> 9.61G); the README states the weights are otherwise identical, so quality is unchanged by keeping the head. The box-side fact (banked 11-26 vehicle run): the file has NO standalone nextn self_attn/mlp - the head is shared-head design (nextn.{eh_proj,enorm,hnorm,shared_head_norm}, shared with the main block by design), and the current mlx_lm glue's MTPDecoderLayer expected standalone weights -> MTP-ON load fault, MTP-OFF build clean (pre-registered fault class; no retry-forever).

1. KEEP the high-precision head (the shipped -mtp build, 0.35G) = RECOMMENDED: the HBM budget absorbs it (9.61G + 0.35G is inside the 16G design with q8_0 KV), the acceptance config is the proven one (the published bench used the shipped head), and it matches the lane's banked convention (draft head bf16 - `MTP6_DRAFT_HEAD=bf16` on the 9B/27B gauntlet vehicles). Expected: no acceptance tax vs the published 54.2% class.
2. int8 head (~0.18G) / 4-bit head (~0.12G): only worth it if the last-G discipline bites (residual HBM pressure); the plot says the acceptance tax is tolerable (all quants within ~2-4 pts). These require a re-quant of the 15 head tensors (the repo ships per-file `tensor-allocation` dumps; the -mtp dump lists the 15 head tensors, so the set is auditable without opening the model). Not recommended for the first pass.
3. Drop -mtp (the non-mtp 9.26G file): the fallback for runs where the speculative path is off - but 0.35G comes back for nothing, so prefer the -mtp file and simply not using the head (the head sits idle in HBM at a 0.35G cost the budget absorbs).
4. Draft-head width arms (`MTP6_DRAFT_HEAD` int2/int2w/bf16/bf16full, the in-tree 9B-vehicle probe class): the 27B front's reference is the shipped bf16 head (option 1); the int2 class is a 9B-vehicle probe, not a 27B recommendation - listed so the probe class is not confused with the 27B config.
5. The MTP-ON load-fault class is the gating item: monky's MTP items must first record the fault class (or a clean build if the vehicle's MTP glue has been fixed for the shared-head design) - if it faults, the MTP-off fallback number is the recorded one, no retry-forever (pre-registered, banked 11-26).

## Category 3 - the MTP-speculative lever (named in the first-card era, expanded)

The named lever: MTP speculative decoding on the quantized-preserving 2.5-bit weights - one main pass + one 0.35G draft pass ~= 2 tokens per ~9.95G of weight reads; ISTA's own card ships the MTP speculative-decoding plots for exactly these files.

- Cost model (arithmetic, DERIVED): AR = 9.61G read per 1 output token. MTP cycle = 9.61G main + K x 0.35G draft + 9.61G verify for ~2.5-2.9 output tokens (54.2% mean acceptance, geometric decay) ~= 20G per ~2.7 tokens ~= 7.4G per output token, i.e. ~1.3x the weight-read efficiency of AR before verify overhead; counting the verify pass honestly (19.2G per ~2.7 tokens) the cycle is ~7.1G/token vs 9.61G/token AR = ~1.35x read efficiency, and the token-identical losslessness gate (the in-tree K=2/K=3 runs are token-identical to plain decode, ALLTOKS prefix-match) means the quality cost is ZERO by construction. (The 11-26 card's "~2.4x" figure counted draft-pass-only cycles; this card's honest verify-included figure is ~1.35x read efficiency - both are arithmetic, the measured number decides.)
- Reference bands to beat (all published/oracle, none ours): ISTA's llama.cpp bench 101.6-118.0 tok/s (their hardware); the lane's mission targets 144.3 t/s MTP vs 87 t/s non-MTP AR (llama.cpp anchors); the in-lane 9B-class vehicle banked 111.01 t/s at K=3 (0.3.0 record protocol); the in-lane 27B-class AR standing 73.45 t/s (the -16% class). Expected on the box: MTP-on is the headline number for the front - it upgrades any AR-only estimate.
- The oracle cross-check exists and is cheap: llama.cpp itself has the `--mtp` speculative type (DRAFT_MTP; draft-token count via the spec draft-max/`-ns` class), and the -mtp file is a standard GGUF that runs unmodified in llama.cpp - so the same-file llama.cpp MTP-on number on the box is the reference arm for the vehicle's MTP-on number (the 11-26 oracle already established the same-file AR control class at 41.2 t/s vs the vehicle's 0.28 t/s; the MTP control extends that).
- The kernel-path reality check (11-26 record, banked): the vehicle's current Q2-class file-GEMM path runs 0.28 t/s vs the 41.2 t/s same-file oracle (147x) - so the MTP lever's gain is only as good as the underlying AR path; the MTP-on arm measures the lever, the 147x gap is the separate stack lever (i-quant conversion + route IQ2_S to the rdna4 mmq kernels, 12 refs, in-tree verified).

The 4-item queue stands unchanged; these three are the additions, ordered after item 1 (the AR baseline) and before item 3 (the file A/B):
